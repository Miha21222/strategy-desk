# CLAUDE.md — Strategy Desk

Agent onboarding for this repo. UI strings are Russian, code/comments/prompts are English.

## What it is

Electron desktop chat shell over the `tradingview` MCP server (tvmcp, Python, `C:\Users\Admin\Projects\tradingview-mcp`)
using `@anthropic-ai/claude-agent-sdk`. The SDK spawns the user's Claude Code binary and reuses the login in `~/.claude`.
No telemetry, no paywall, no account of its own. (The SDK's platform package does ship a ~226 MB native
`claude.exe`, which is most of the installer; the app still uses the user's own login, never its own.)

## How tvmcp is started

The installer carries tvmcp — its sources, its `uv.lock` and a `uv.exe` — and the app builds the Python
environment for it on first run, inside `userData`. The user needs neither a clone nor a `uv` of their own.

```
resources/tvmcp/**               the payload (extraResources, NOT app.asar: uv is a separate process)
resources/uv.exe                 the uv that builds the environment
<userData>/py/venv               the environment; `python.exe -m tvmcp` is what everything spawns
<userData>/py/provisioned.json   {lockHash, uv, at} — "built, and built from this uv.lock"
```

`src/main/runtime-spec.ts` (pure, tested) turns those paths into an environment and a spawn spec, and every
tvmcp spawn in the app goes through it: the MCP server (`mcp.ts`), the `--check` probe (`status.ts`) and the
deterministic CLI (`tv-cli.ts`). `src/main/runtime.ts` is the Electron half — it resolves the paths at boot and
reports; it installs nothing.

**Two modes, decided by whether the payload exists, never by a setting.** No payload (a dev run) = EXTERNAL:
`uv` from PATH plus the checkout in `settings.tvmcpPath`, exactly as before bundling. Payload present =
BUNDLED. The preflight shows `uv` + `tvmcpClone` in one mode and `tvmcpRuntime` in the other.

To exercise the bundled path in a dev run, put a payload where `binaryRoots` looks — the repo root:

```
npm run stage:tvmcp && cp -r build/tvmcp-payload tvmcp && cp build/uv.exe uv.exe
DESK_SMOKE=runtime npm run dev            # minutes, ~600 MB into userData
rm -rf tvmcp uv.exe "$APPDATA/strategy-desk/py"
```

Landmines:

- **A Windows venv is not relocatable.** `Scripts/python.exe` is a stub that reads `home=` out of `pyvenv.cfg`.
  A prebuilt one would die on the first other machine; that is why the app builds it locally.
- **`uv sync --frozen` cannot resolve.** If `uv.lock` has drifted from `pyproject.toml`, the first run fails on
  the user's machine and nothing on their side can repair it — `scripts/stage-tvmcp.mjs` runs `uv lock --check`
  and refuses to stage the drift.
- **Long paths.** `uv sync` into a directory near Windows' 260-character limit fails with `os error 3` while
  persisting a temporary file. `%APPDATA%/strategy-desk/py` is short; a deep test directory is not.
- **Caches want to be written next to the code they belong to.** numba and `__pycache__` would land in the
  installation directory — read-only on a per-machine install, wiped by the uninstaller — so `NUMBA_CACHE_DIR`
  and `PYTHONPYCACHEPREFIX` point into `userData`; see `runtimeEnv`.
- **The environment outlives the app**: `deleteAppDataOnUninstall` is false, so the settings carry
  «Очистить рантайм» (`runtime:clear`).

## The knowledge base (gt-rag) — the second MCP server

The installer also carries the course the owner studied — gt-rag's content plus its server — and offers it to
the model as `gt-database` (`mcp__gt-database__gt_*`: search, page, images, health, re-index).

**One environment, not two.** gt-rag's dependencies (chromadb, fastembed, rapidfuzz) live in tvmcp's OPTIONAL
`kb` extra, and `provisionSpec` adds `--extra kb` whenever the kb payload is present. gt-rag's `server.py`
prefers fastmcp when it finds one, because tvmcp pins `mcp<2` through fastmcp while a standalone gt-rag
install uses `mcp>=2` — the same eight tools either way. A second venv would have doubled ~600 MB to gain
nothing.

```
resources/gt-rag/server.py, gt_rag/   the code (read-only, stays in the installation dir)
resources/gt-rag/raw/, images/        course markdown + chart screenshots (read-only, ~125 MB)
resources/gt-rag/store/               the prebuilt ChromaDB store — a SEED, copied per user
resources/gt-rag/model/               the fastembed model (~240 MB), optional — also a seed
<userData>/py/kb/data                 GT_RAG_DATA: the copy chroma may open read-write
<userData>/py/kb/model                FASTEMBED_CACHE_PATH
<userData>/py/kb/seeded.json          {seedHash, at} — "seeded, and from this payload"
```

`GT_RAG_DATA` / `GT_RAG_RAW` / `GT_RAG_IMAGES` are what make that split possible; they were added to gt-rag
for this. Why split at all: **ChromaDB opens its sqlite file read-write even to answer a query**, and
huggingface_hub writes lock files into the model cache — neither may happen inside an installation directory
that a per-machine install makes read-only and the uninstaller wipes. The images stay in the payload
precisely because nothing ever writes to them.

Landmines:

- **Both libraries opt into telemetry by default.** chromadb's `anonymized_telemetry` is `True` and
  posts to PostHog on every `PersistentClient`; huggingface_hub sends its own on a model load. The app
  promises none, so `buildKbEnv` sets `ANONYMIZED_TELEMETRY=False` and `HF_HUB_DISABLE_TELEMETRY=1` in
  EVERY mode, a developer's clone included.
- **`PYTHONIOENCODING=utf-8` is load-bearing.** The content is Russian and the server answers in JSON on
  stdout; a Windows cp1251 default turns the first «→» in a hit into a UnicodeEncodeError — a server that
  dies mid-answer, with a traceback that says nothing about encodings until you read the last line.
- **The seed is a copy, not a download**, so `kb-import` is the one task that spawns nothing. Its marker is
  written only after a clean copy, so an interrupted one reads as "not seeded" rather than as done.
- **`Read` is part of the capability**: `gt_image_path` answers with a path to a chart screenshot that the
  model then opens, so the permission preset allows `mcp__gt-database` and `Read` together.
- Staging switches: `SD_BUNDLE_KB=0` (no knowledge base at all), `SD_BUNDLE_KB_MODEL=0` (content but no
  model — the app then offers the download as the `kb-model` task). With `SD_BUNDLE_KB=0` the payload
  directory is still created, empty: `extraResources` fails the build on a missing source, and an empty
  directory is exactly what `initRuntimePaths` reads as "nothing shipped".
- **The content is course material.** gt-rag's own README says `data/` is copyrighted and not
  redistributable; an installer built with it hands that content to whoever downloads it. `SD_BUNDLE_KB=0`
  is the build for that case.

To exercise it in a dev run, junction both payloads into the repo root (a junction needs no admin rights and
saves copying ~420 MB) and provision for real:

```
npm run stage:tvmcp && npm run stage:gtrag
cmd //c mklink /J tvmcp build\tvmcp-payload && cmd //c mklink /J gt-rag build\gtrag-payload
cp build/uv.exe uv.exe
DESK_SMOKE=runtime npm run dev     # builds the venv WITH the kb extra
DESK_SMOKE=kb npm run dev          # seeds the store, then asks it how many chunks it holds
rm -rf tvmcp gt-rag uv.exe "$APPDATA/strategy-desk/py"
```

## Long operations: tasks

The things the app may do FOR the user — provision the runtime, fetch the headless browser, seed the
knowledge base, download its embedding model, register and authenticate the official TradingView MCP —
share one runner (`src/main/tasks.ts`, contract in
`src/shared/tasks.ts`). **The renderer names a task id, never a command**, the same rule `tv:call` keeps for
tools. Nothing starts at launch: a task runs from a button in the preflight, which shows the command before
running it and streams the output while it runs.

The official MCP's registration lives in Claude Code's own store rather than ours, because that is where its
OAuth token lives — and that store is consulted even though the app passes `mcpServers` programmatically with
`strictMcpConfig: true` and `settingSources: []` (verified 2026-09-22: `status: connected, source: dynamic`).
`claude mcp add` runs with `-s user`: the default `local` scope is private to one working directory, and the
app's own directory is not where the user works.

## Conventions

- Add a new IPC call in three places: `src/shared/api.ts` (type), `src/preload/index.ts` (bridge), `src/main/ipc.ts` (handler).
- All user-visible strings go through `t('section.key')` from `src/renderer/i18n`; add keys to `ru.ts` first.
- Use only documented Agent SDK options (see `node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts`); the SDK is ESM-only
  and is loaded with dynamic `import()` from the CJS main bundle.
- Chat events are the union `ChatEvent` in `api.ts`; the renderer treats the trailing assistant message with `at === -1` as live.
- Secrets never cross IPC; the renderer sees `hasApiKey` / `hasOauthToken` only.
- CSP is `default-src 'self'; style-src 'self' 'unsafe-inline'` (meta tag in `index.html`). No external scripts/styles.
- Keep `tv-launch.ts` small: it will move into the tvmcp tool `tv_desktop_launch`.
- **Anything read at runtime from a file that ships with the app** goes through `src/main/resources.ts`
  (`readResource()` / `resourceCandidates()`), never through `process.cwd()` or a bare `app.getAppPath()`.
  The order is dev cwd → `app.getAppPath()` (= `app.asar` when packaged) → `process.resourcesPath`, and the
  cwd candidate is dropped when `app.isPackaged`, because an installed app's cwd is wherever the shortcut
  points. A new shipped file needs **three** edits: the read site, `files:` in `electron-builder.yml`, and a
  line in `DESK_SMOKE=pack` (`runPackSmoke` in `src/main/index.ts`) so `npm run dist:check` notices when it
  stops shipping. Dev cannot catch this on its own — in dev everything is in the working directory anyway.
- Commit messages end with the attribution line the session's system reminder gives.

## The `panel` contract (stage 4)

A workflow may declare a `panel` in its `workflow.yaml`. The app then drives a whole
trading day **deterministically**, with no model turn, through the tvmcp CLI
(`uv --directory <tvmcp> run tv <tool> '<json>'`). MCP tools are called by the model;
the CLI is how the app calls the same implementations itself. A call costs ~2.5 s of
local CPU (Python + fastmcp import) and zero tokens.

```yaml
panel:
  kind: session-watch | risk-desk
  sentinel: {...}        # tv_sentinel_start spec, minus `day` and `levels` (the app fills both)
  levels: {...}          # tv_scan_levels args; symbol/provider default to the sentinel's
  levelNames: [...]      # which computed level names the watch gets; empty = all
  clocks: [{name, at, tz}]
  askModelOn: [RANGE_CLOSED, BREAK_CONFIRMED, SWEEP, CLOCK]   # the ONLY events that buy a turn
  calendar: {...}        # tv_calendar_check args (the app adds `date`)
  risk: {...}            # tv_risk_guard args (the app adds `today`, `journal`, `rules_path`)
  journal: {...}         # tv_journal_load args (the app adds `path_or_name`)
  prompts: {event, verdict, review}   # templates; {event_json} {events_json} {state_json} {date} ...
  pollFloorSeconds: 5
```

Rules the code enforces, and that a new workflow must not have to restate:

- **The sections are permissive records** passed to the tool almost verbatim, so a second
  workflow declares another instrument, session or rules file with **no code change**. The
  tool validates them (pydantic, `extra="forbid"`); a bad section shows as a call error in
  the panel, not a crash at load.
- **No strategy number ever lives in TypeScript.** Sessions, ranges, thresholds, prop limits
  and prompt text belong in the yaml, the prompt block or the user's own rules JSON.
- **Polling**: the interval is whatever the run's `next_poll_after_s` asks for, clamped to
  [5 s, 15 min]; a stopped, finished, session-closed or replayed run is never polled again;
  the loop is chained, so one run never has two polls in flight.
- **One turn per poll at most**, for the newest event whose type is in `askModelOn`; the
  prompt carries every qualifying event of that poll. A replay sends no turns at all.
- The run id is `desk-<workflowId>-<date>`, so a restart **reattaches** (an "already exists"
  refusal from `tv_sentinel_start` is the signal to attach, not an error to show).

## The `tv:call` allowlist

The renderer names a tool, never a command. `src/shared/panel.ts` holds the list and
`src/main/ipc.ts` enforces it before anything is spawned:

```
tv_sentinel_start  tv_sentinel_poll  tv_sentinel_status  tv_sentinel_stop
tv_scan_levels     tv_calendar_check tv_risk_guard       tv_journal_load
tv_desktop_status
```

Read-and-poll only. Nothing here draws on the user's chart, writes a journal row, saves a
Pine script or places anything. Adding a tool to this list is a security decision: it must
be read-only or write nothing but its own run file, and the reason goes in the commit.

## Preflight and the setup wizard (stage 5, partial)

The diagnosis lives in two halves: `src/shared/preflight.ts` owns the contract and the pure
`buildChecks(cfg, facts)` mapping, `src/main/preflight.ts` owns the probes. The renderer shows
the same list twice — step by step in `SetupWizard`, all at once in Settings → «Диагностика».

Two rules that are not negotiable, and that the tests pin down:

- **Preflight never runs a network or destructive command by itself.** `git clone`, the uv
  installer, `uv sync`, the Claude login and "close TradingView" come back as a `copy` fix:
  copyable text plus one sentence saying what will happen. The app performs exactly three
  fixes on its own — launch TradingView, switch the `cdpPort` setting, open a native file
  picker — and each is something the user pressed a button for. Adding a fix kind that acts
  on its own is the same kind of decision as adding a tool to the `tv:call` allowlist.
- **It caches nothing.** "Проверить заново" invalidates the tvmcp boot cache first, because a
  stale green light is worse than a slow check.

A check carries i18n *keys*, not sentences (`detailKey` + `vars`), so Russian stays in
`src/renderer/i18n/ru.ts` and the main process holds no UI text. A skipped wizard step is
remembered in `settings.setupSkipped`, and the feature it weakens must say so itself —
never fail silently later.

## Stage roadmap

0. Chat shell: SDK bridge, lights, quick actions, chats/shelves, settings, help (this stage).
1. Live verification with TradingView + tvmcp, polish streaming edge cases, `canUseTool` scoping for the extended preset.
2. Structured cards: render `nextsteps/chartcard/stressreport/prodata/briefreport/healthdata/workflowstate` natively.
3. Workflows per shelf: strategy builder, indicator (Pine) builder, performance review, journal, IB day.
4. The day panel: deterministic CLI polling, the `panel` contract, the IB-day and V1B3 workflows.
5. Document import (pdf-parse), attachments in chat, exports, packaging. Done: the setup wizard, the
   preflight diagnosis, the "Live field notes" prompt section (`data/copilot-notes.md`, overridable
   with `settings.fieldNotesPath`), and the Windows installer (NSIS per-user, own icon,
   `npm run dist:check`). Still open: code signing, electron-updater (auto-update is off on
   purpose — no release channel, no certificate), official MCP auth flow.
